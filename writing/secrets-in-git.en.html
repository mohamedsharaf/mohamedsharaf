A database password in a config file. An .env file that slipped past .gitignore. A cloud key pasted into a test script “just for now”. Secrets end up in Git repositories every single day, and automated scanners find public ones within minutes.

Deleting the file doesn’t remove the secret

Git remembers everything. If a key was committed and later removed, it is still in the history, in every clone, in every fork and in the CI system’s cache. Rewriting history is possible, but you can’t rewrite the copies other people already have. So the rule is simple: a secret that was ever committed is a leaked secret.

The first hour

  1. Revoke and replace the secret. Before anything else. Create a new key, update the systems that use it, then disable the old one.
  2. Check whether it was used. Look at the provider’s logs for activity from unknown places since the commit date.
  3. Then clean the history if the repository is public or widely shared, so the old value stops spreading. This is tidying up; the revocation is the actual fix.
  4. Find out how it happened, so it doesn’t happen next week.

How to stop the next one

  • Keep secrets out of code entirely. Use environment variables injected at deploy time, or a secrets manager from your cloud provider or a dedicated tool. Code should contain the name of a secret, never its value.
  • Commit an example, not the real file. Keep an .env.example with empty values in the repository and the real .env in .gitignore.
  • Scan before the commit. A pre-commit hook with a scanner such as Gitleaks or TruffleHog stops most mistakes on the developer’s own machine.
  • Scan on the server too. GitHub, GitLab and others can scan pushes and block ones that contain known secret formats. On GitHub, push protection is on by default for public repositories, and you can enable it for private ones.
  • Scan what you already have. Run a scanner over the full history of your existing repositories once. Old leaks are still leaks.
  • Use short-lived credentials where you can, for example CI pipelines that get temporary cloud access instead of a permanent key stored in settings.

Don’t forget the other places

Secrets also leak through CI logs that print environment variables, screenshots in tickets, chat messages and Docker images built with a key inside. The same rule applies everywhere: if it was exposed, rotate it.

Most of this costs an afternoon to set up. Cleaning up after a leaked cloud key can cost far more, sometimes in a single night.
